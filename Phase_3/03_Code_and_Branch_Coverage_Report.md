## 1. Executive Summary

This document constitutes the formal **Code and Branch Coverage Report** for the Electronics Store Inventory Management System (ESIMS), submitted under **Deliverables Part-3 (Code & Branch Coverage Report - 3 Marks)**.

In software engineering, structural code coverage assesses the thoroughness with which an automated test suite exercises the source code. While statement coverage measures the percentage of executable lines invoked, **branch coverage** measures whether every decision point (e.g., `if-else`, `try-except`, loop conditions) was traversed through both its `True` and `False` branches.

## 2. Measurement Methodology & Reproduction Configuration

Coverage was measured using industry-standard `Coverage.py 7.17.2` integrated directly with the Django automated test runner.

### 2.1 Execution Command

From the `src/` directory with the virtual environment activated:

```powershell
# 1. Run complete automated test suite with branch instrumentation
python -m coverage run --branch --source=accounts,inventory,reports,audit,nfr_tools,esims manage.py test inventory accounts reports audit nfr_tools

# 2. Generate textual console summary report with missing line numbers
python -m coverage report -m --omit="*/tests.py,*/test_*.py,*/migrations/*"

# 3. Generate interactive HTML coverage dashboard
python -m coverage html --omit="*/tests.py,*/test_*.py,*/migrations/*"
```

### 2.2 Omission Rationale

The `--omit` argument explicitly filters out:
1. `*/tests.py` & `*/test_*.py`: Automated test definitions must not measure their own lines of code, as doing so artificially inflates coverage figures.
2. `*/migrations/*`: Django migrations are autogenerated schema metadata files that contain declarative operations rather than procedural application logic.

By applying this filter, the reported metrics reflect **100% pure production application source code**.

## 4. In-Depth Analysis of Uncovered Lines and Partial Branches

Academic rigor requires not only celebrating high numbers, but justifying precisely why certain lines and branches remained unexercised:

### 4.1 `esims/asgi.py` & `esims/wsgi.py` (0% Coverage — 8 statements)
* **Explanation:** These modules contain boilerplate entry points for ASGI and WSGI servers (e.g., Daphne, Uvicorn, Gunicorn) deployed in live production hosting environments.
* **Justification:** Django's automated test runner invokes views and middleware in-process via `django.test.Client` without spinning up an external asynchronous or WSGI network gateway. These 8 lines are pure deployment hooks and have zero impact on application business logic.

### 4.2 `accounts/roles.py` (98% Coverage — Branch `56->51`)
* **Branch Analysis:** Line 56 is the loop condition in `sync_roles_and_permissions()`: `for perm_code in permissions:`.
* **Explanation:** The partial branch `56->51` represents the loop exit condition when the permissions list is empty. In the test suite, every standard role (Admin, Staff, Viewer) is configured with non-empty permissions lists; hence, the loop is always entered and completes all iterations.

### 4.3 `inventory/forms.py` (81% Coverage — Lines 30, 36)
* **Branch Analysis:** Relates to `clean_component_id()` in `ComponentForm`.
* **Explanation:** Lines 30 and 36 handle defensive checks when `self.instance.pk` is modified dynamically during an edit form submission while the original component ID in the database was concurrently removed by another thread. In single-user unit test scenarios, this race condition branch does not execute.

### 4.4 `inventory/views.py` (97% Coverage — Lines 36-38)
* **Branch Analysis:** Fallback `except IntegrityError:` block in `component_add()`.
* **Explanation:** Form-level validation (`ComponentForm.clean()`) traps duplicate component IDs and invalid fields *before* the database save is attempted. Lines 36-38 serve as a second-tier defensive backstop in case an unexpected low-level database constraint fails. Because form validation is 100% effective, this catch-all branch is rarely triggered.

### 4.5 `nfr_tools/availability.py` (70% Coverage) & `nfr_tools/database_recovery.py` (80% Coverage)
* **Branch Analysis:** Uncovered lines are located inside:
  * `if __name__ == "__main__":` command-line argument parsers (`argparse`).
  * Infinite `while True:` polling loops designed for continuous multi-day background daemon monitoring.
* **Justification:** The automated test suite executes calculation functions and programmatic API methods directly (`calculate_availability()`, `backup_database()`, `restore_database()`) rather than executing blocking infinite loops or CLI shell wrappers during unit test execution.

## 5. Control Flow Graph (CFG) & Cyclomatic Complexity Analysis

To demonstrate structural test design, the control flow of the critical decision method `Component.availability_status` was analyzed:

### 5.1 Control Flow Logic

```python
def availability_status(self):
    # Node 1: Entry
    if self.quantity == 0:          # Decision 1
        return "Out of Stock"       # Branch 1A (True) -> Exit
    elif self.quantity <= self.minimum_stock:  # Decision 2
        return "Low Stock"          # Branch 2A (True) -> Exit
    else:
        return "In Stock"           # Branch 2B (False) -> Exit
```

### 5.2 Branch Execution Matrix

| Decision Point | Condition Evaluated | Test Case Exercising `True` Branch | Test Case Exercising `False` Branch | Branch Coverage |
|:---:|:---|:---|:---|:---:|
| **Decision 1** | `quantity == 0` | `AvailabilityDisplayTests.test_availability_status_out_of_stock` ($Q=0$) | `AvailabilityDisplayTests.test_availability_status_low_stock` ($Q=8$) | **100% (Both paths taken)** |
| **Decision 2** | `quantity <= minimum_stock` | `AvailabilityDisplayTests.test_availability_status_low_stock` ($Q=8, M=10$) | `AvailabilityDisplayTests.test_availability_status_in_stock` ($Q=50, M=10$) | **100% (Both paths taken)** |

* **Cyclomatic Complexity ($V(G)$):** $V(G) = P + 1 = 2 + 1 = 3$ independent basis paths.
* **Basis Path Coverage Achieved:** **3 / 3 paths (100% Basis Path Coverage)**.
